# 0005 — Базовые конфигурации Target'ов в targets/ и отдельный сценарий ESP32

Дата: 2026-10-19

## Статус

Принято.

## Контекст

ADR-0001 задаёт Специализацию как одноразовый merge Target-ветки в main проекта. Ранее базовые конфигурации каждого семейства жили в Target-ветках целиком. Требование: базовые настройки по памяти микроконтроллеров должны лежать в Базе, в разделе `targets/`, чтобы Специализация начиналась с готового набора (memory.x + Cargo.toml + build.rs + .cargo/config.toml), а не с нуля.

## Решение

В Базе, в `targets/<family>/`, хранится полный базовый шаблон на каждое поддерживаемое семейство:

```
targets/
  stm32f1xx/  stm32f3xx/  stm32f4xx/  stm32g0xx/
  rp2040/     nrf528xx/   gd32vf1xx/  esp32/
    memory.x          # базовые регионы памяти чипа-представителя + директивы chip:/board:
    Cargo.toml        # HAL + рантайм (cortex-m-rt / riscv-rt) + release-профиль
    build.rs         # копирует memory.x в OUT_DIR для -Tlink.x
    .cargo/config.toml  # target-тройка + runner probe-rs
    README.md        # специализация под Board, команды сборки/прошивки/отладки
```

- `memory.x` несёт базовые значения чипа-представителя семейства и **обязательные директивы `chip:` / `board:`** (их читает тестировщик и сверяет с фактом по IDCODE; `board: TBD` означает «уточнить при Специализации»).
- Target-ветка уточняет шаблон под семейство/Board (объёмы памяти, feature HAL, `--chip` у probe-rs); Специализация переносит файлы в корень проекта.

**ESP32 — отдельный сценарий** внутри `targets/esp32/`: xtensa-тулчейн через `espup` (не rustup), прошивка через `espflash` по UART (не probe-rs), линковщик настраивает esp-hal (`linkall.x`) — поэтому там нет `memory.x` и `build.rs`. Подготовка окружения — `./setup.sh --esp32`.

**Рассмотренные альтернативы**: держать конфигурации только в Target-ветках — отклонено, дублирует одинаковую механику (build.rs, link.x, runner) и заставляет каждую ветку стартовать с нуля; единый мульти-таргет Cargo-проект — отклонён по ADR-0001; вписать ESP32 в общий probe-rs-путь — отклонен, так как требует искажения общего шаблона (иная память, иной программатор, иной тулчейн).

**Consequence**: База содержит 8 каталогов-шаблонов, из которых специализированный проект после merge забирает один — остальные удаляются при Специализации (или остаются как справочник; решает проект). Значения памяти в `memory.x` — базовые точки отсчёта, не гарантия под конкретную Board. Проверка чипа/платы в HIL-тестировании опирается на директивы `chip:`/`board:` в `memory.x`.
